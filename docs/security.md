# Модель безопасности Kervax

Главная гарантия: **панель — только приёмник метрик.** Даже при полной
компрометации панели атакующий не получает доступ к серверам, а лишь может
испортить/подделать то, что видно в дашборде.

## 1. Связь только наружу

Агент **ничего не слушает** и **не исполняет команды**: в нём нет ни сетевого
слушателя (`net.Listen`/HTTP‑сервера), ни запуска шелла/процессов. Он только
периодически **POST‑ит метрики** на панель по HTTPS. Панель физически не может
подключиться к серверу — там нет открытого порта, к которому можно постучаться.

## 1b. Адреса источников agent API

На аутентифицированных маршрутах agent API токен остается обязательным. Проверку
IP дополнительно включает настройка
`KERVAX_AGENT_SOURCE_GUARD` (по умолчанию `0`). Сохранение адресов в карточке
сервера не включает общий фильтр; его состояние видно в разделе «Сеть».

При включенной проверке разрешены текущий основной IP сервера (`agent_ip`) и
явно заданный список `agent_source_ips`. После замены основного IP старый адрес
разрешен только если явно добавлен в дополнительный список. Отчеты, ранее
замеченные адреса и данные установки
через прокси не добавляют доверенные источники автоматически. Если основной IP
и дополнительный список пусты, для этого сервера остается проверка только токена.

Для NAT или HTTP-прокси укажите фактический IP источника в «Сеть -> Дополнительные
IP источников агента», по одному в строке, например `198.51.100.10` или
`2001:db8::10`. Допустимы до 16 отдельных IPv4/IPv6; подсети, имена и пустые
элементы отклоняются. IPv6 приводится к каноническому виду, IPv4-mapped IPv6
становится IPv4, дубликаты убираются. Права редактора на этот список совпадают с
правами на основной IP и учитывают группы серверов. Поле ответа
`agent_source_guard_enabled` доступно только для чтения и отражает настройку панели.

Перед включением настройте и проверьте доверенные reverse proxy на хосте панели,
проверьте прямые и проксируемые маршруты агентов, явно добавьте нужные источники
NAT и HTTP-прокси. Заголовок пересылки от произвольного клиента не должен
определять его адрес. Список источников дополняет токен, не заменяет хостовый
фаервол и не делает недоверенный прокси доверенным.

## 2. Агент непривилегирован и зажат

- Системный юзер `kervax`: без домашнего каталога, shell `/usr/sbin/nologin`.
- systemd‑хардненинг: `NoNewPrivileges=true`, `ProtectSystem=strict`,
  `ProtectHome=true`, запись разрешена **только** в `/opt/kervax-agent/bin`
  (`ReadWritePaths`). Единственная capability — `CAP_SYSLOG` (read‑only на
  `/dev/kmsg`, чтобы узнать имя OOM‑убитого процесса).

## 2b. Сама панель тоже работает не от root

- Бэкенд и планировщик идут под пользователем `kervax` (uid 10001). Контейнер
  стартует от root ровно на время подгонки владельца смонтированного тома и
  сразу сбрасывает привилегии — так обновление не ломает уже существующий
  `./data`, созданный прежним образом.
- Фронтенд — nginx, собранный под работу от uid 101 и порт 8080: 80-й порт
  панели не нужен, наружу её публикует реверс-прокси.
- У всех контейнеров `no-new-privileges:true`.

## 2c. Root-хелперы: что делает то, что агент делать не может

Часть данных непривилегированному агенту недоступна принципиально — сроки PKI
кластера лежат под root, а секреты Flux не отдаст ни один разумный RBAC. Такие
задачи выполняют отдельные скрипты (`agent/*-setup.sh`), которые вы ставите
руками и осознанно; агент их не запускает и запустить не может.

- Живут в `/lib65/kervax`, запускаются systemd-таймером, результат кладут
  готовым разбором в `/var/lib/kervax/*.json` (0644). Агент только читает файл.
- Панель командовать ими не может: в ответе агенту нет ничего, кроме интервала
  и пожелания обновиться (см. раздел 3).
- Наружу отдают выводы, а не сырьё: `kubeexpiry-setup` шлёт вид, место, дату и
  состояние `Ready` — ни ключей, ни значений токенов, ни их длины.

Отдельно про сетевой запрос. Срок токена не хранится внутри самого токена —
его знает только форж, поэтому `kubeexpiry-setup` спрашивает **тот хост, что
указан в URL источника Flux** (self-hosted GitLab спрашивает сам себя, а не
gitlab.com). Токен используется ровно для этого запроса, никуда не пишется и
ноду не покидает. Не хотите этого запроса — не ставьте хелпер: без него панель
просто не знает сроков, всё остальное работает как раньше.

Необязательный helper `docker-origin-setup` проверяет локально производные
образы `wollomatic/socket-proxy`. Он только читает локальный Docker API, сверяет
неизменяемый digest родителя и каждый добавленный слой, допускает лишь пустые
заглушки точки монтирования сокета. При каждом обновлении проверяет закрытый
набор правил API только для чтения, внутреннюю сеть и ограничения прав
контейнера. Имя, локальный тег и непрозрачный хеш сами по себе ничего не
доказывают. Без свежего полного доказательства предупреждение о сокете остается;
привилегии и прочий доступ к хосту проверяются отдельно. Монтирование сокета
только для чтения не ограничивает Docker API.

Helper ставится явно на Docker-узел командой из панели. Нужен Python 3,
сборщик находится в `/lib65/scripts/`, результат проверки - в
`/var/lib/kervax/report.d/docker-origin.json`. Значения окружения и команды
контейнера в панель не передаются. Helper не меняет и не перезапускает
контейнеры. Неизвестные правила команд, изменение программы и недоступная
история образа сохраняют предупреждение.

## 3. Что панель вообще может сказать агенту

Ответ панели агенту — структура ровно из двух полей:

```go
type config struct {
    Interval int         // как часто слать метрики
    Update   *updateWish // «обновись до версии X» — только пожелание
}
```

Никаких «выполни», «прочитай файл», «открой порт». Максимум — сменить интервал или
**попросить** обновиться.

## 3b. Проверка сайта агентом: почему это не дыра

Сайт, закрытый белым списком, панель проверить не может — снаружи соединение
рвут. За неё это делает агент на самом сервере, и панель говорит ему «проверь
такой-то адрес». Звучит как ровно та команда, которой в разделе 3 нет, поэтому
важно, чем она ограничена.

**Агент соединяется только с localhost.** Адрес он подставляет сам; из URL берёт
имя (Host и SNI), схему, порт и путь. Панель не может послать его на другой хост
— ни на соседний сервер, ни во внутреннюю сеть. Захваченная панель не превращает
парк агентов в сканер: максимум, что она узнает, — как отвечает сам этот сервер,
что она и так знает от него же.

**Наружу уходят факты, а не страница.** Код ответа, задержка, текст ошибки и
«нашлось ли ключевое слово» — поиск слова агент делает у себя. Содержимое
закрытых страниц панель не получает, не хранит и не пишет в логи.

**Вердикт выносит панель.** Агент не решает, «работает» сайт или нет: он
сообщает факты, а пороги, повторы и инциденты остаются в панели — теми же
правилами, что и для обычных мониторов.

Обратная сторона честная: в задании на проверку едут заголовки и пароль
basic-авторизации этого монитора, если они заданы. Это те же данные, которыми
сайт на этой ноде и так пользуется, но знать об этом стоит.

## 4. Обновление — подпись, а не доверие панели

Агент ставит новый бинарь **только если выполнены все три условия**:

1. **Подпись манифеста верна** — Ed25519, проверяется **вшитым в бинарь публичным
   ключом**. Приватная половина — офлайн (`agent-signing/kervax-agent.key`), в
   `.gitignore`, **никогда** не на панели и не в деплой‑тарболе.
2. **Версия строго новее** текущей — анти‑откат (нельзя вернуть старую, возможно
   дырявую, версию).
3. **sha256 и размер** скачанного бинаря совпадают с подписанным манифестом.

Замена бинаря атомарная (`rename`), перезапуск — `exec` того же бинаря (не
произвольной команды).

## 5. Модель угрозы: панель взломана

Атакующий с полным контролем над панелью имеет: публичный ключ (он и так публичный),
хеши токенов агентов (только для входящей аутентификации агента **к** панели),
возможность отдавать любые файлы. Он **НЕ может**:

- подделать подпись манифеста — **нет приватного ключа** → любой его бинарь агент
  отвергнет;
- откатить агент на старую версию (анти‑откат);
- выполнить команду, открыть шелл, прочитать файлы, «пролезть» на сервер — агент
  этого не умеет в принципе.

Худшее: соврёт в UI про метрики, поменяет интервал, попросит обновиться на **уже
легитимно подписанную** версию. Доступа к серверу — ноль.

## 5b. Резервный сервер бэкапов: копия, которую не удалить с основного

Резервный сервер держит вторую копию выбранных restic-репозиториев с одного или
нескольких основных серверов бэкапов. Смысл в том, чтобы копию нельзя было стереть,
даже взломав основной сервер бэкапов, клиента или панель.

- **Резервный забирает сам.** Раз в сутки он заходит на основной по SSH учеткой
  `kervax-mread`. У основного нет ни ключа, ни входа на резервный, отправить туда
  что-то или удалить он не может.
- **Учетка на основном только читает.** В `authorized_keys` ключ резервного стоит с
  `restrict`, `from="<адрес резервного>"` и принудительной командой
  `kervax-mirror-serve mirror-<id>`. Эта команда умеет две вещи: список файлов и
  выдачу файлов, и только из репозиториев, которые разрешили этому резервному.
  Шелла, проброса портов и записи нет.
- **Файлы проверяются и не перезаписываются.** Файлы restic зашифрованы и названы
  по sha256 содержимого. Перекачка идет непривилегированной учеткой в песочнице
  systemd в отдельный каталог, потом root на резервном сверяет хеш с именем и кладет
  файл в копию, только если такого еще нет. Подмененный файл не возьмется, а
  уже лежащий не перезапишется.
- **Удаления доходят с задержкой.** Пропавшее на основном держится в копии
  `KEEP_DAYS` дней (по умолчанию 30). Если за одну перекачку пропала большая часть
  снапшотов или данных (`FREEZE_PCT`, по умолчанию 50%), репозиторий опустел или
  сменился его config, копия замораживается: из нее ничего не удаляется и ничего
  нового не берется, пока root на резервном не разморозит ее командой
  `kervax-mirror-helper unfreeze`.
- **Проверка без ключей.** Каждый файл копии раз в `CHECK_DAYS` дней (по умолчанию
  7) перечитывается и сверяется с хешем. Испорченный откладывается и забирается
  заново. Пароли репозиториев резервному не нужны и на нем не лежат.

Что может панель: отметить сервер резервным, сказать основному, какому резервному
что можно читать, сказать резервному, откуда и что забирать, поставить копию на
паузу и попросить перекачать сейчас. Чего она **не может**: удалить копию или ее
файлы, сменить адрес, порт или ключ хоста уже известного основного (новое значение
ждет подтверждения `kervax-mirror-helper accept` на резервном), разморозить копию,
поменять сроки хранения. Сроки и каталог задаются только в
`/etc/kervax/mirror.conf` на резервном.

Худшее при взломанной панели: копирование новых данных встанет (пауза или чужой
адрес, который резервный не примет без подтверждения), это увидит алерт
`backup_mirror` на резервном. Старые копии останутся.

Восстановление: `restic -r <каталог копии> snapshots` с паролем репозитория из
сейфа. Саму копию не трогайте: если restic попросит починить индекс, делайте
`restic repair index` на отдельной копии каталога.

## 6. Реальная граница доверия

- **Приватный ключ** — корень доверия. Держите офлайн, под пасфразой, бэкап в
  пароль‑менеджере. Перед любой выкладкой:
  `tar tzf … | grep -iE 'agent-signing|\.key$'` → должно быть пусто.
- **Хост сборки** — в цепочке доверия: он производит байты, которые вы подпишете.
  Для максимума доверия собирайте локальным Docker (`сборка == подпись`,
  reproducible — хеши совпадают байт‑в‑байт). Если собираете на build‑хосте по SSH,
  держите его чистым.

Порядок релиза/подписи и восстановление при потере ключа — в
[`docs/agent-releases.md`](agent-releases.md).
