# Релиз и обновление агента Kervax

Как вручную собрать, подписать и раскатить новую версию агента — без каких‑либо
внешних сервисов. Всё делается двумя-тремя командами.

## В двух словах: почему это безопасно

Корень доверия — **офлайн приватный ключ** (`agent-signing/kervax-agent.key`).

- Агенты ставят новый бинарь **только если** его манифест подписан этим ключом,
  версия **строго новее** текущей (анти‑откат) и **sha256 совпал**.
- Приватный ключ **никогда** не попадает на панель и не коммитится в git.
- Значит, даже взломав панель, атакующий **не подпишет** свой бинарь и ничего на
  агенты не раскатит. Панель — только раздатчик уже подписанных байт.

Подробнее про модель угроз — в [`docs/security.md`](security.md).

---

## Что нужно один раз

- **Python 3.11+** с пакетом `cryptography`
  (`pip install cryptography`).
- **Docker** на машине, где запускаете релиз — для воспроизводимой сборки
  (сборка == подпись, максимум доверия). Либо build‑хост по SSH (см. ниже),
  но он тогда попадает в цепочку доверия.
- Всё остальное (`agent-signing/*.py`) уже в репозитории.

---

## Шаг 0. Один раз: создать ключ подписи

Только если ключа ещё нет (`agent-signing/kervax-agent.key` отсутствует).

```bash
python agent-signing/keygen.py          # ключ шифруется пасфразой (рекомендуется)
# или:  python agent-signing/keygen.py --plain   # без пасфразы (небезопасно)
```

Создаст:
- `agent-signing/kervax-agent.key` — **приватный** ключ. Права `0600`, в `.gitignore`.
  **Забэкапьте его и пасфразу в пароль‑менеджер** — потеряете, и обновлять агентов
  будет нечем (придётся генерить новый ключ и переустанавливать всех агентов).
- `agent-signing/kervax-agent.pub` — **публичный** ключ. Он вшивается в бинарь
  агента при сборке. В апстриме его НЕТ намеренно: ключ у каждой установки свой,
  и агенты, собранные с чужим публичным ключом, доверяли бы чужим подписям. В
  своём форке или деплой‑репозитории коммитить его нормально — это не секрет.

Если сгенерировали `--plain`, позже закройте ключ пасфразой:
```bash
python agent-signing/protect_key.py
```

> Публичный ключ **вшивается в бинарь автоматически** при сборке (`release.py` берёт
> его из `kervax-agent.pub`). Править `agent/main.go` руками не нужно.

## Шаг 1. Собрать и подписать новую версию

1. **Поднимите версию** в `agent/main.go`:
   ```go
   const version = "1.21"   // было 1.20
   ```

2. **Соберите и подпишите** (номер должен совпасть с тем, что в `main.go`):
   ```bash
   python agent-signing/release.py 1.21
   ```
   Если ключ зашифрован — спросит пасфразу.

Что делает `release.py`:
- собирает статические бинари `amd64` и `arm64` с вшитым публичным ключом
  (в Docker: `сборка == подпись`);
- считает `sha256`/размер, пишет канонический `manifest.json`, подписывает его
  офлайн‑ключом и **само‑проверяет** подпись;
- кладёт в `agent-dist/`: `manifest.json`, `manifest.sig`,
  `kervax-agent-amd64`, `kervax-agent-arm64`.

**Сборка без локального Docker** (build‑хост по SSH — он попадает в цепочку доверия):
```bash
# либо запишите цель в agent-signing/build-host.txt (напр. root@203.0.113.10 или ssh-alias)
KERVAX_BUILD_SSH=my-build-host  python agent-signing/release.py 1.21
```
`release.py` предупредит, что build‑хост в цепочке доверия. Для максимума доверия —
поднимите Docker локально.

## Шаг 2. Выложить артефакты на панель

Панель раздаёт агентам файлы из своего `agent-dist/`
(`/api/agent/manifest`, `/api/agent/manifest.sig`, `/api/agent/download/<arch>`).
Значит, свежие `agent-dist/*` должны попасть в образ панели.

Если панель в Docker (типовой случай): передеплойте её **вместе с `agent-dist/`** и
пересоберите backend:

```bash
# из корня репозитория, на машине с доступом к панели:
docker compose up -d --build backend
```

> Проверьте, что деплой **включает** `agent-dist/` и **исключает** секреты:
> `tar tzf <ваш_тарбол> | grep -iE 'agent-signing|\.key$'` — должно быть **пусто**.
> `agent-dist/` содержит только подписанные бинари и манифест — их выкладывать можно.

Убедиться, что панель видит новую версию:
```bash
curl -s https://ВАША-ПАНЕЛЬ/api/agent/manifest        # version должна быть 1.21
```

> Если панель **сама собирает** бинарь агента (сборочный слой в `backend/Dockerfile`),
> задайте в `.env` `KERVAX_AGENT_PUBKEY=<содержимое kervax-agent.pub>` — тогда
> собранные панелью бинари несут ваш публичный ключ. `release.py` вшивает его в любом
> случае; env нужен только для панельной сборки.

## Шаг 3. Раскатить на агенты

Раскатка — это лишь «пожелание»: панель просит агент обновиться, а агент сам
проверяет подпись/хеш/анти‑откат и ставит только валидный бинарь.

**Через UI:** `Серверы` → (по желанию сначала одну ноду — canary) → «Обновить все».

**Через API:**
```bash
TOKEN=... # JWT админа панели
# все включённые агенты:
curl -s -X POST https://ВАША-ПАНЕЛЬ/api/servers/agent-update \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1.21"}'
# только выбранные (canary):
#   -d '{"version":"1.21","server_ids":[3]}'
```

Агент подхватит «пожелание» на своём следующем отчёте (в пределах интервала),
скачает бинарь, проверит и перезапустится тем же PID.

---

## Шаг 4. Проверить, что обновились

```bash
# через API: посмотреть agent_version у серверов
curl -s https://ВАША-ПАНЕЛЬ/api/servers -H "Authorization: Bearer $TOKEN" \
  | python -c 'import sys,json; [print(s["name"], s["agent_version"]) for s in json.load(sys.stdin)]'
```
Или на самой ноде:
```bash
journalctl -u kervax-agent -n 5 --no-pager   # «kervax-agent 1.21 → https://…»
```

Если агент отказался — в логе будет причина: неверная подпись, не новее текущей
(анти‑откат) или несовпадение sha256. Это штатная защита, а не баг.

## Установка / переустановка агента на сервере

Первичная установка (команду с токеном даёт панель: `Серверы → Добавить сервер`):
```bash
curl -fsSL https://ВАША-ПАНЕЛЬ/api/agent/install.sh | sh -s -- https://ВАША-ПАНЕЛЬ <ТОКЕН>
```
- Ставит бинарь в `/opt/kervax-agent/bin` (владелец — непривилегированный юзер `kervax`),
  конфиг в `/etc/kervax-agent.conf`, systemd‑юнит `kervax-agent`.
- Второй агент на том же сервере (метрики в другую панель) — третьим аргументом:
  `… | sh -s -- https://ПАНЕЛЬ2 <ТОКЕН2> panel2` → юнит `kervax-agent@panel2`.

**Переустановка** нужна, когда меняется сам systemd‑юнит (OTA обновляет только
бинарь, не юнит). Просто выполните ту же install‑команду ещё раз — юнит перезапишется,
агент перезапустится. Токен можно взять прежний или сротировать в панели.

---

## Правила безопасности (коротко)

- Приватный ключ (`agent-signing/kervax-agent.key`) — **офлайн**, под пасфразой,
  бэкап в пароль‑менеджере. Никогда: в git, на сервере, в деплой‑тарболе.
  Перед выкладкой всегда: `tar tzf … | grep -iE 'agent-signing|\.key$'` → пусто.
- Публичный ключ (`kervax-agent.pub`) — не секрет, но в апстрим не попадает:
  свой ключ создаёт `keygen.py`, чужой доверять нельзя.
- Для максимума доверия собирайте локальным Docker (`сборка == подпись`). Если
  собираете на build‑хосте — он в цепочке доверия, держите его чистым.
- Версию только повышайте — анти‑откат не даст поставить более старую.

---

## Если потеряли приватный ключ

Обновлять существующих агентов больше нечем (они верят старому публичному ключу).
Порядок восстановления:
1. `keygen.py` — новая ключпара (новый `kervax-agent.pub`).
2. `release.py <версия>` — собрать агент с новым публичным ключом.
3. Выложить на панель.
4. **Переустановить** агент на каждой ноде install‑командой (старые агенты новый
   ключ не примут — нужен новый бинарь). После этого OTA снова работает.
